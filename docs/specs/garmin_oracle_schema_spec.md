# Garmin Oracle Schema Specification, Version 1

Last Modified: 2026-07-15

## 1. Purpose

This document defines the first relational Oracle schema used to load portable
Garmin export packages produced by Garmin AI Coach. It complements
`garmin_oracle_export_spec.md`, which defines the portable file format and the
future loader responsibilities.

The schema is intentionally small. It stores only activity and daily
heart-rate data currently required by the coach. HRV is explicitly outside
version 1 because the available exports contain no populated HRV metrics.

All Oracle object and column names use uppercase letters and underscore
separators.

## 2. Scope and principles

Version 1 stores these datasets:

* Activity summaries.
* Activity type classification.
* Heart-rate and power zone durations per activity.
* Fastest split metrics and split summaries per activity.
* Daily heart-rate summaries and heart-rate samples.
* Import-batch audit metadata.

Version 1 does not store HRV, Garmin credentials, session tokens, FIT/GPX/TCX
files, GPS coordinates, routes, media, unneeded account data, or raw JSON
payloads.

The design uses the natural Garmin identifiers where available. Repeated
one-to-many structures are represented by child tables rather than repeated
columns. All training data is separated by `OWNER_ID`, an opaque local export
identifier such as `LOCAL_USER`; it must not contain a Garmin username or email
address.

## 3. Relationship overview

```text
GARMIN_OWNER
 ├─ GARMIN_IMPORT_BATCH
 ├─ GARMIN_ACTIVITY
 │   ├─ GARMIN_ACTIVITY_HR_ZONE
 │   ├─ GARMIN_ACTIVITY_POWER_ZONE
 │   ├─ GARMIN_ACTIVITY_FASTEST_SPLIT
 │   └─ GARMIN_ACTIVITY_SPLIT_SUMMARY
 └─ GARMIN_DAILY_HEART_RATE
     └─ GARMIN_DAILY_HR_SAMPLE

GARMIN_ACTIVITY ──> GARMIN_ACTIVITY_TYPE
```

## 4. Tables

### 4.1 `GARMIN_OWNER`

Represents one logical owner of imported Garmin data.

| Column | Oracle type | Rules |
|---|---|---|
| `OWNER_ID` | `VARCHAR2(100)` | Primary key. Opaque local identifier. |
| `CREATED_AT_UTC` | `TIMESTAMP WITH TIME ZONE` | Not null. |

### 4.2 `GARMIN_IMPORT_BATCH`

Records a package processed by the loader. It is audit metadata and does not
contain training payloads.

| Column | Oracle type | Rules |
|---|---|---|
| `IMPORT_BATCH_ID` | `NUMBER(19)` | Primary key, generated by the database. |
| `OWNER_ID` | `VARCHAR2(100)` | Not null, foreign key to `GARMIN_OWNER`. |
| `EXPORT_SCHEMA_VERSION` | `NUMBER(5)` | Not null. |
| `EXPORTER_VERSION` | `VARCHAR2(40)` | Not null. |
| `EXPORT_BEGIN_DATE` | `DATE` | Not null. |
| `EXPORT_END_DATE` | `DATE` | Not null. |
| `MANIFEST_SHA256` | `VARCHAR2(64)` | Not null. |
| `LOADED_AT_UTC` | `TIMESTAMP WITH TIME ZONE` | Not null. |
| `LOAD_STATUS` | `VARCHAR2(20)` | Not null; `LOADED` or `FAILED`. |
| `ERROR_MESSAGE` | `VARCHAR2(1000)` | Null for a successful load; must not contain payloads or secrets. |

The loader must enforce a unique constraint on `(OWNER_ID, MANIFEST_SHA256)` to
prevent the same package being loaded twice.

### 4.3 `GARMIN_ACTIVITY_TYPE`

Stores Garmin's reusable activity classification.

| Column | Oracle type | Rules |
|---|---|---|
| `ACTIVITY_TYPE_ID` | `NUMBER(10)` | Primary key; Garmin `typeId`. |
| `PARENT_ACTIVITY_TYPE_ID` | `NUMBER(10)` | Nullable Garmin `parentTypeId`. |
| `ACTIVITY_TYPE_KEY` | `VARCHAR2(80)` | Not null; Garmin `typeKey`. |
| `SPORT_TYPE_ID` | `NUMBER(10)` | Nullable Garmin `sportTypeId`. |

### 4.4 `GARMIN_ACTIVITY`

from one owner being confused with an activity from another owner.

| `ACTIVITY_NAME` | `VARCHAR2(255)` | Nullable. |

| `START_TIME_LOCAL` | `TIMESTAMP` | Nullable; converted from `startTimeLocal`. |
| `DURATION_SECONDS` | `NUMBER(12,3)` | Not null. |
| `ELAPSED_DURATION_SECONDS` | `NUMBER(12,3)` | Nullable. |

| `ELEVATION_GAIN_METERS` | `NUMBER(14,3)` | Nullable. |
| `ELEVATION_LOSS_METERS` | `NUMBER(14,3)` | Nullable. |
| `CALORIES` | `NUMBER(12,3)` | Nullable. |
| `STEPS` | `NUMBER(12)` | Nullable. |
| `LAP_COUNT` | `NUMBER(8)` | Nullable. |
| `ACTIVITY_TRAINING_LOAD` | `NUMBER(12,4)` | Nullable. |
| `MODERATE_INTENSITY_MINUTES` | `NUMBER(10,3)` | Nullable. |
| `VIGOROUS_INTENSITY_MINUTES` | `NUMBER(10,3)` | Nullable. |
| `AVERAGE_HEART_RATE` | `NUMBER(8,3)` | Nullable. |

| `AVERAGE_SPEED_MPS` | `NUMBER(12,6)` | Nullable. |

All distance, duration, speed, power, and running-dynamics columns preserve
the units used by the export contract. The loader must not silently convert
them to kilometres, minutes, or kilometres per hour.

### 4.5 `GARMIN_ACTIVITY_HR_ZONE`

| Column | Oracle type | Rules |
|---|---|---|
| `OWNER_ID` | `VARCHAR2(100)` | Primary key component; activity owner. |
| `GARMIN_ACTIVITY_ID` | `NUMBER(19)` | Primary key component; activity identifier. |
| `ZONE_NUMBER` | `NUMBER(3)` | Primary key component; positive integer. |
| `DURATION_SECONDS` | `NUMBER(12,3)` | Not null. |

Foreign key: `(OWNER_ID, GARMIN_ACTIVITY_ID)` references `GARMIN_ACTIVITY`.

### 4.6 `GARMIN_ACTIVITY_POWER_ZONE`

This table has the same columns and primary key as
`GARMIN_ACTIVITY_HR_ZONE`, but stores power-zone durations.

### 4.7 `GARMIN_ACTIVITY_FASTEST_SPLIT`

| Column | Oracle type | Rules |
|---|---|---|
| `OWNER_ID` | `VARCHAR2(100)` | Primary key component. |
| `GARMIN_ACTIVITY_ID` | `NUMBER(19)` | Primary key component. |

| `DURATION_SECONDS` | `NUMBER(12,3)` | Not null. |

This accommodates all exported `fastestSplit_<distance>` fields without a

### 4.9 `GARMIN_DAILY_HEART_RATE`

Stores one daily summary row, including days with no heart-rate samples.

| Column | Oracle type | Rules |
|---|---|---|
| `OWNER_ID` | `VARCHAR2(100)` | Primary key component; foreign key to `GARMIN_OWNER`. |
| `CALENDAR_DATE` | `DATE` | Primary key component. |
| `RESTING_HEART_RATE` | `NUMBER(8,3)` | Nullable. |
| `LAST_SEVEN_DAYS_AVG_RESTING_HEART_RATE` | `NUMBER(8,3)` | Nullable. |
| `MIN_HEART_RATE` | `NUMBER(8,3)` | Nullable. |
| `MAX_HEART_RATE` | `NUMBER(8,3)` | Nullable. |

### 4.10 `GARMIN_DAILY_HR_SAMPLE`

Stores the Garmin `heartRateValues` time series. The export descriptors confirm
that each pair is `TIMESTAMP`, `HEARTRATE`; timestamps are 13-digit Unix epoch
milliseconds in the observed export and are converted to UTC timestamps by the
loader.

| Column | Oracle type | Rules |
|---|---|---|
| `OWNER_ID` | `VARCHAR2(100)` | Primary key component. |
| `CALENDAR_DATE` | `DATE` | Primary key component. |
| `SAMPLE_TIMESTAMP_UTC` | `TIMESTAMP WITH TIME ZONE` | Primary key component. |
| `HEART_RATE_BPM` | `NUMBER(8,3)` | Nullable. |

Foreign key: `(OWNER_ID, CALENDAR_DATE)` references
`GARMIN_DAILY_HEART_RATE`.

The loader validates that the descriptors are exactly `timestamp` and
`heartrate` before loading samples. It rejects a package with a different
descriptor layout rather than guessing its interpretation.

## 5. Constraints and indexes

The DDL must create all primary keys and foreign keys stated above. It should
also create these indexes:

* `GARMIN_ACTIVITY(OWNER_ID, START_TIME_UTC)` for date-range coaching queries.
* `GARMIN_ACTIVITY(ACTIVITY_TYPE_ID)` for sport filtering.
* `GARMIN_DAILY_HR_SAMPLE(OWNER_ID, SAMPLE_TIMESTAMP_UTC)` for time-series
  queries.

No index is required solely for `GARMIN_IMPORT_BATCH` beyond its primary key and
unique `(OWNER_ID, MANIFEST_SHA256)` constraint.

## 6. Loader mapping rules

The future Oracle loader must validate the export manifest and map records as
follows:

| Export dataset or field | Oracle target |
|---|---|
| `activities.ndjson` activity summary | `GARMIN_ACTIVITY` and `GARMIN_ACTIVITY_TYPE` |
| `hrTimeInZone_<n>` | `GARMIN_ACTIVITY_HR_ZONE` |
| `powerTimeInZone_<n>` | `GARMIN_ACTIVITY_POWER_ZONE` |
| `fastestSplit_<n>` | `GARMIN_ACTIVITY_FASTEST_SPLIT` |
| `splitSummaries` | `GARMIN_ACTIVITY_SPLIT_SUMMARY` |
| `daily_heart_rate.ndjson` summary fields | `GARMIN_DAILY_HEART_RATE` |
| `heartRateValues` | `GARMIN_DAILY_HR_SAMPLE` |

The loader ignores `daily_hrv.ndjson` in version 1 after verifying its checksum
through the manifest. It uses idempotent `MERGE` operations based on each
table's primary key.

## 7. Deferred items

The following are intentionally deferred:

* HRV tables and loading, until non-empty HRV payloads are available.
* GPS tracks, activity streams, FIT files, routes, media, and raw JSON storage.
* Training plans, nutrition data, assistant conversations, and derived coaching
  assessments.
* A separate staging schema. The initial loader may parse NDJSON directly and
  use transaction boundaries per package.
